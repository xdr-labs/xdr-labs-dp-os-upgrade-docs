# DP Offline Ubuntu Upgrade Guide

This site is designed to be followed **from top to bottom**. If this is your first time performing the upgrade, start with **Step 1** and continue in order.

## What this guide does

For the Full upgrade path:

```text
Prepare Mirror Server
  → DP Ubuntu 16.04
  → 18.04
  → 20.04
  → 22.04
  → 24.04
  → DP 6.6.0 Phase 2
  → Final validation
```

The Mirror Server downloads and validates the required files in advance. During the upgrade, the DP hosts retrieve prepared material from that server over **HTTP/TCP 80**.

## Follow these five steps

| Step | What you do | Finish condition |
| --- | --- | --- |
| **1. Upgrade Work Plan** | Choose the correct path, maintenance order, snapshots, and go/no-go gates | Plan and prerequisites confirmed |
| **2. Ubuntu 24.04 Server Installation** | Build the Mirror Server when a new server is required | Ubuntu 24.04, disk, network, SSH verified |
| **3. Mirror Server Setup** | Install Mirror Manager, prepare files, enable HTTP, verify readiness | **Upgrade Readiness = PASS** |
| **4. DP Offline Ubuntu Upgrade** | Follow fresh Menu 7 commands through OS hops and Phase 2 | Ubuntu 24.04 + DP 6.6.0 bringup complete |
| **5. Post-Upgrade Validation** | Verify OS, DP version, clusters, services, NTP/DNS, and operations | All required validation checks pass |

## Which path applies to my DP?

| Current state | Use | Result |
| --- | --- | --- |
| Supported DP 6.2.x–6.5.0 on Ubuntu 16.04 | **Full OS Upgrade + Phase 2** | Ubuntu 24.04 + DP 6.6.0 |
| Supported DP 6.2–6.5 already on Ubuntu 24.04 | **Phase 2 Only** | DP 6.6.0 |
| Healthy DP 6.6.0 on Ubuntu 24.04 | Normally no upgrade | No change |

The current Mirror Manager target is **DP 6.6.0**. Do not mix historical 6.5.0 procedures into the active workflow.

## Three rules to remember

1. **Prepare first.** Do not touch the DPs until the Mirror Server reports `Upgrade Readiness = PASS`.
2. **Use fresh generated commands.** Menu 7 is the authoritative source for the current Mirror Server IP, preparation mode, and cluster configuration.
3. **Keep recovery available.** Create the required hypervisor snapshot(s) before destructive work and keep them until final validation and change-control closure.
