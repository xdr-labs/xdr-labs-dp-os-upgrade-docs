# 1. 업그레이드 작업 계획

여기서 시작하십시오. 이 페이지는 설치나 업그레이드를 수행하기 전에 전체 작업 순서를 설명합니다.

## 목표

전체 업그레이드의 최종 상태는 다음과 같습니다.

```text
Ubuntu 16.04의 DP 6.2.x–6.5.0
  → Ubuntu 18.04
  → Ubuntu 20.04
  → Ubuntu 22.04
  → Ubuntu 24.04
  → DP 6.6.0 Phase 2 Bringup
  → 최종 검증
```

모든 Ubuntu LTS 단계(Hop)를 순서대로 수행해야 합니다.

## 업그레이드 경로 선택

| 현재 DP 상태 | 사용할 경로 | 최종 상태 |
| --- | --- | --- |
| Ubuntu 16.04의 지원 DP 6.2.x–6.5.0 | **Full OS Upgrade + Phase 2** | Ubuntu 24.04 + DP 6.6.0 |
| 이미 Ubuntu 24.04인 지원 DP 6.2–6.5 | **Phase 2 Only** | DP 6.6.0 |
| 이미 Ubuntu 24.04 + 정상 DP 6.6.0 | 일반적으로 업그레이드 불필요 | 변경 없음 |

## Maintenance Window 계획

아래 시간은 **3노드 DL + 3노드 DA** 구성 예시의 계획 기준이며 보장 시간은 아닙니다.

| 단계 | 예시 소요 시간 | 수행 시점 |
| --- | --: | --- |
| Mirror Server 준비 | **2–3시간** | Production Maintenance Window 이전 |
| DP 사전 점검 및 서비스 Pause | **약 30분** | Maintenance 시작 시점 |
| 전원 OFF Snapshot/Checkpoint Gate | **약 30분** | DP 사전 점검 및 서비스 Pause 완료 후, Ubuntu 업그레이드 전 |
| 전체 노드 Ubuntu OS 업그레이드 | **약 1.5–2시간** | Snapshot/Checkpoint Gate 완료 후 |
| 전체 노드 Phase 2 Staging | **약 2시간** | Maintenance Window, 네트워크 여유 시간 포함 권장 |
| DL Cluster Bringup | **약 2시간** | Staging 완료 후 |
| DA Cluster Bringup | **약 2시간** | DL 정상 확인 후 |
| 최종 검증 및 Resume | **15–30분** | Maintenance 종료 전 |

예시 다이어그램 기준 Production Maintenance Window는 약 **8–9시간**이며, Mirror Server 준비는 사전에 완료하는 것을 전제로 합니다. 실제 시간은 노드 수, 스토리지 성능, WAN/LAN 처리량, 재부팅 시간, 패키지 상태, Cluster 복구 시간에 따라 달라집니다.

<Info>
  Maintenance 시간을 줄이기 위해 Ubuntu LTS Hop을 건너뛰거나 DL Readiness 확인 전에 DA Bringup을 시작하지 마십시오.
</Info>

## 전체 작업 순서

<Steps>
  <Step title="서비스 중단 전에 Mirror Server 준비">
    Configuration, Download/Prepare, HTTP Distribution, Readiness 검증을 완료하고 최신 DP Client 명령을 생성합니다. 필수 Gate는 **Upgrade Readiness = PASS**입니다.
  </Step>
  <Step title="DP 사전 점검 및 서비스 Pause">
    연결 상태와 현재 버전을 확인하고, 현재 생성된 절차에서 지시하는 경우 DP 서비스를 Pause합니다. Snapshot/Checkpoint에 들어가기 전에 사전 점검과 Pause가 완료되어야 합니다.
  </Step>
  <Step title="전원 OFF Snapshot/Checkpoint Gate 수행">
    DP 사전 점검 및 서비스 Pause 완료 후, 현재 Upgrade Client가 Shutdown 후 Snapshot/Checkpoint 생성을 요구하면 필요한 모든 노드에서 해당 Gate를 완료합니다. 이 Gate가 끝나기 전에는 Ubuntu 업그레이드를 시작하지 않습니다.
  </Step>
  <Step title="모든 대상 노드의 Ubuntu 업그레이드">
    Snapshot/Checkpoint Gate 완료 후 `16.04 → 18.04 → 20.04 → 22.04 → 24.04` 순서대로 수행합니다. 각 Hop은 별도의 통제된 전환 단계입니다.
  </Step>
  <Step title="모든 대상 노드에 DP 6.6.0 Phase 2 Staging">
    최종 Cluster Orchestration 전에 DL Master, DL Worker, DA Master, DA Worker의 Staging/Preflight를 모두 완료합니다.
  </Step>
  <Step title="DL Cluster 먼저 Bringup">
    DL Master에서 최종 Orchestration을 실행하고 DL Cluster가 정상 상태가 될 때까지 기다립니다.
  </Step>
  <Step title="그 다음 DA Cluster Bringup">
    DL Gate가 통과한 후에만 DA Master에서 최종 Orchestration을 실행합니다.
  </Step>
  <Step title="전체 시스템 Resume 및 검증">
    변경 작업을 종료하기 전에 DP 버전, Node Readiness, Pod, Host Service, NTP, DNS, License, Web UI 및 정상 운영 상태를 확인합니다.
  </Step>
</Steps>

## Go / No-Go Gate

현재 단계가 완료되기 전에는 다음 주요 단계로 넘어가지 마십시오.

| Gate | 필수 결과 |
| --- | --- |
| Mirror Server | `Upgrade Readiness = PASS` |
| 생성 명령 | 현재 Mirror Server IP 기준 최신 Menu 7 출력 |
| Snapshot/Checkpoint Gate | DP 사전 점검 및 서비스 Pause 이후, 현재 Client가 명시적으로 요구한 Snapshot 작업 완료 |
| Phase 1 | Snapshot/Checkpoint Gate 이후 모든 대상 노드에서 Ubuntu 24.04 검증 완료 |
| Phase 2 Staging | Staging/Preflight가 Bringup 준비 완료 상태 |
| DL Bringup | DA 시작 전에 DL Bringup 성공 완료 |
| 최종 검증 | DP 6.6.0 및 모든 필수 Cluster/Service 정상 |

## 안전 수칙

- 파괴적 DP 작업 전에 **모든 DP VM에 필요한 Hypervisor Snapshot**을 생성하십시오.
- 이 프로젝트는 지원되는 OS 또는 DP Runtime Rollback 명령을 제공하지 않습니다. 현장에서 안전하게 복구할 수 없는 파괴적 장애의 복구 방법은 Snapshot Restore입니다.
- Mirror Server IP 또는 관련 설정이 변경되면 이전에 생성된 명령을 재사용하지 마십시오.
- 과거 6.5.0, `apt-cacher-ng`, Full Mirror Runbook을 현재 6.6.0 Mirror Manager 절차와 혼용하지 마십시오.
- 현재 설치된 Mirror Manager가 생성한 Menu 7이 환경별 DP 명령의 기준입니다.
